On a Monday the pipeline goes red on a repository nobody has pushed to for three days. The failing step is the test suite. The exit code is **137**.

137 is SIGKILL. Everyone reads it the same way: out of memory, the runner ran out of room, add memory or split the suite. We read it that way too, and we were wrong for most of a day.

The suite was fine. What had moved was an image tag, under a repository that had not.

## An exit code names a mechanism, not a cause

137 means the process received SIGKILL: something killed it outright. The kernel's out-of-memory killer is its most frequent sender, which is why the number has come to mean "OOM" in everyone's head.

That is not what the number says. Here the sender was Docker, and the reason was that the container the process was running inside had just restarted underneath it.

## The ninety-second control experiment

Before diagnosing anything, there is one question to settle: **is it the code, or is it the world?**

The repository had not changed in three days, which makes the test cheap. Re-run the last green job, unchanged, today.

We re-ran only the test job of the commit from three days earlier — the one that had passed at the time. It failed, identically, at the same place.

```
Tests  completed  failure  —  exit code 137, at the same place
```

Ninety seconds, and the whole category of "something we wrote" was eliminated. The move costs nothing, needs no hypothesis, and exists on every CI platform. We reached for it far too late.

## The measurement that killed the wrong hypothesis, and that we did not believe

We still believed the memory story, so we measured it: the full suite locally against a real database, with the container's memory sampled every three seconds.

```
546 tests to the end
peak 669 MiB   on a machine that offers 7.7 GB
```

No leak, nothing close to a limit. That should have buried the theory within the hour. It did not, because **the exit code kept saying "memory" louder than the measurement said "no"**.

This is the part of the story that does not tell itself willingly: we held a hypothesis against a measurement that contradicted it, for hours, because a famous number agreed with it.

## The container had been hiding the error for a day

The logs showed the application booting, migrations running, a line saying the server was ready, the web server loading its configuration — and then nothing. The container exited and restarted, silently, in a loop. No error, no trace, no complaint.

One command printed what a day of reading logs had not:

```
frankenphp adapt --config /etc/caddy/Caddyfile
parsing caddyfile tokens for 'mercure': unknown mercure directive "demo"
```

**When a service exits without explaining itself, ask its configuration to validate itself.** Every serious server can — `caddy validate`, `nginx -t`, `apachectl configtest` — and they print on stdout what the service swallows at startup.

## What had actually changed

The base image was `dunglas/frankenphp:1-php8.4-alpine`. That `1-` is not a version: it is a moving pointer to the newest 1.x.

On 4 October it went from **1.12.7 to 1.13.0**. A minor release, published by people who owe us nothing, pulled by our own build on the next run. Two things broke with it:

- its Mercure module no longer accepts the `demo` directive, which our development configuration had been passing for months;
- it stopped shipping `/var/log/caddy`, the directory our own configuration writes access logs to.

The second one is the more uncomfortable. **Nothing in our repository ever created that directory.** It came with the base image, we had been relying on it for months, and we did not know we were.

## The same lesson as a fortnight ago, one floor down

A [piece published here on upgrading the OS under Docker](/en/upgrading-the-os-under-docker/) ended on a structural finding: the compose files are the one piece of production configuration nobody owns. Not baked into the image, exercised by no test, not even copied by the deploy. **The fault that survives is in the file the pipeline never opens.**

This is the same sentence one floor further down. The pipeline does not merely fail to open the base image: **it pulls it, on every build, without review**. A floating tag is a dependency that enters production with nobody's signature on it.

We review a one-line change to a controller. We do not review a minor version of the runtime underneath it, because nothing asks us to.

## Three lines of fix, one day of diagnosis

Pin the base to the patch version that was actually running, drop the obsolete directive, create the log directory in our own Dockerfile instead of inheriting it. The usual ratio — and the reason what is worth writing down is the route, not the patch.

Then we pinned the rest by digest: Postgres, Redis, the PDF renderer, the development mail catcher. The last one was not even tagged: it floated on `latest`. **All four had already moved** since the images on our machines were pulled.

## Pinning is also a version decision, and it has a price

This is the part that is easy to leave out, so it goes here.

Pinning by digest does not freeze time politely: you have to choose *which* bytes. Choosing today's means performing the upgrade you had been doing by accident until then. For us: Postgres from 16.11 to 16.15, and three containers recreated — on a single host, a few seconds where the site does not answer.

That cost we accept, and it is written down elsewhere. What is not acceptable is discovering it. So the upgrade was tested locally first — the database came back on its existing data directory, the suite passed on a freshly migrated schema — and the outage was named in the commit **before** the deploy.

And finally: a pin that can only be moved blindly is a pin nobody moves, which turns a security practice into a security problem. So there is now one command that prints what each pinned tag resolves to today. Moving a pin becomes a decision somebody takes, not something that happens to them.

## Good practices

- **Re-run the last green job before diagnosing.** Unchanged code failing today eliminates an entire category of hypothesis in ninety seconds.
- **When a service exits silently, ask its configuration to validate itself.** One line, where logs gave nothing for a day.
- **Pin third-party images by digest, not by tag.** A tag is a name, and names can be re-pointed at different bytes by people who owe you nothing.
- **Give yourself a command that shows the drift**, so updating a pin is a decision rather than an omission.
- **Declare what you depend on**, including the boring parts. A directory that happens to exist in a base image is a dependency with no contract.

## Points to watch

- An exit code names a mechanism, not a cause. 137 is SIGKILL, and the kernel's OOM killer is only its most famous sender.
- **A repository that has not changed is not a system that has not changed.** Floating tags, base images, runner images, registries: all of it moves while the git history stands still.
- The symptom can sit two causal steps from the cause. A directive removed, so a container loops, so a process is killed: nothing in the error mentions the first step.
- Pinning freezes security fixes too. It is the right default, and it is only healthy alongside something that makes the drift visible — and the habit of going to look at it.
- Writing it up afterwards flatters the route. We held the wrong hypothesis for hours against a measurement that contradicted it.
